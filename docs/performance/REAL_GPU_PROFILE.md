## Reading this

- The engine is vsync-capped at 60 FPS by default, so "max=60/61" means "never bottlenecked," not "the ceiling." All three scenarios stay at or near that cap on this hardware.
- The "Small" scenario's min=21 FPS / max frame_time=118ms is a one-frame transient right at scene load (shader/material compilation, nav mesh baking) — it recovers to a steady 55-61 FPS within the first second and never dips again; it is not a sustained low-FPS scenario. The stress scenario's max=128ms is the same kind of transient at the moment `_sync_staff_agents()` instantiates 150 new nodes in one frame — a real game reaching 150 staff does so by hiring one at a time over many in-game days, never 150 in a single frame, so this is a harsher one-frame spike than actual play produces.
- 150 staff agents push primitives from ~2.4K (empty office) to ~6.2M/frame — each `StaffAgent`'s 7-part modular body (P39/P40) is plain `MeshInstance3D` geometry, not instanced/batched. FPS stays healthy here (avg 59.2, matching `docs/production/KNOWN_ISSUES.md`'s "150-agent stress scene has 16x CPU headroom" from the P44 CPU-only pass — this confirms the GPU side has real headroom too on this hardware), but the primitive count is the concrete number a future `MultiMesh`/instancing pass (prompt 20, not done in this pass — no bottleneck was measured to justify it yet, and this project's own rule is "medir antes de optimizar") would target first if a lower-spec GPU ever struggled.
- Draw calls stay low throughout (76 → 356 → 2176) — well within budget for any GPU from the last decade, including integrated graphics like this environment's AMD APU.

## Limitations (explicit, not glossed over)

- **Single run, this container's hardware only** (AMD Radeon integrated graphics via Mesa `radeonsi`/ACO, real direct rendering through an actual X server at `:0` — this is genuinely GPU-rendered, not a software/llvmpipe fallback, but it is this development environment's APU, not necessarily representative of a player's discrete GPU or a lower-spec minimum-target machine).
- No player input was simulated — camera movement, build-mode ghost previews, and UI panel churn all cost more than an idle/AI-only scene; this profile does not cover them.
- No decorative prop-instancing system exists yet to profile against `PERFORMANCE_BUDGET.md`'s separate "500 props" target (see `KNOWN_ISSUES.md` — still an open scope boundary).
- Camera was left at `campaign.gd`'s default; zoomed-in/close-up framing (more screen-space overdraw) wasn't separately measured.
