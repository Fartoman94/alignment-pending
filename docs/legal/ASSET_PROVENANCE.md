## Humanoid pipeline (total-visual-rework pass)

A real bug found and fixed in the supplied generator, not assumed correct from reading it: the original script built a real `Armature` and separate body-part meshes, but only ever did `mesh.parent = armature_object` — a plain hierarchical parent, not a skin binding. No mesh vertex was ever weighted to any bone, so the exported "idle/walk/typing/talk/sit" animations moved the invisible skeleton while every visible mesh stayed rigidly frozen. Confirmed by loading the original script's export in Godot and diffing an idle frame against a played "walk" frame: pixel-identical. Fixed with a full-weight vertex group + real `Armature` modifier per body part (the standard rigid-bind pattern for a blocky low-poly character where each part moves as one rigid unit, not a smoothly deforming surface) — re-verified the same way, this time with the leg pose visibly different between idle and walk frames, across 3 different roles (researcher, safety, team_leader — confirming per-role accessories like glasses/helmet/tie all still attach and export correctly).

Ran the full fixed generator: 24 real, rigged, animated, textured low-poly humanoid characters (8 roles × 3 variants each) with actual faces (eyes/iris/pupils/brows/nose/mouth/ears/hair) — a real visual upgrade over every character model this project has used so far, none of which have a face. Every file loads cleanly in Godot with a working `Skeleton3D` + `AnimationPlayer` (5 real animations per file), verified by rendering, not just checking the file imports.

**Not yet wired into `StaffAgent`, and here's exactly why, so this isn't a vague TODO:** the existing character pipeline (`StaffAgent._build_visual()`) expects a flat hierarchy — a `world` root node containing loose, unskinned mesh parts named `leg_l`/`leg_r`/`arm_l`/`arm_r`, which it manually reparents into hand-built rotation pivots, animated every frame by trig math in `_animate_visual()`. These new characters are structured completely differently — a real `Rig`/`Skeleton3D` with properly skinned meshes and baked `AnimationPlayer` clips — the *better*, standard way to do character animation, but a different code path, not a drop-in replacement. Wiring them in for real means: detecting a model has a `Skeleton3D`+`AnimationPlayer` in `_build_visual()` and branching to a skeletal-animation path instead of pivot construction; mapping `StaffAgent.State` (`IDLE`/`MOVING`/`WORKING`) to the baked animation names (`idle`/`walk`/`typing` or `sit`); and moving `_apply_variation()`'s skin/hair-tint lookup to search `Head`/`Hair` directly under the `Skeleton3D` instead of the `_bob_group` reparenting target it uses today (skinned meshes can't be reparented into a pivot group without breaking their skin binding — that reparenting step doesn't apply to this hierarchy at all). Real, bounded, well-understood work — deliberately not rushed into the one system every scene in this project depends on this late in an already long pass, without room to test it as thoroughly as the rest of this session's changes.

Every new player-facing asset must be added here before merge.

## City backdrop (production-kit integration, kit prompt 10)

Scoped to the kit's own brief for this ("Build a **decorative, low-cost** city layer"), not a spatial/explorable city — `RealEstateManager` stays the deliberate abstract management screen it already is (this ledger's and `KNOWN_ISSUES.md`'s existing "not a literal city map" call, same reasoning already applied to `DatacenterManager`). New `game/src/world/city_backdrop.gd` (`CityBackdrop`, `extends SubViewport`) bakes a small street scene — a handful of the city models above, arranged by `RealEstateManager`'s tier id into "sparse" (garage/garage_plus/small_office), "mid" (medium_office), or "dense" (premium_office/hq_building) — into its own isolated `World3D`, rendered exactly **once** per office build/tier change (`render_target_update_mode = SubViewport.UPDATE_ONCE`), not every frame. `Campaign._office_window()` uses the resulting texture as both the window's albedo (reads under normal lighting) and a heavily-dimmed emission (`CITY_EMISSION_SCALE = 0.12`, keeping the old "glows from across the room" behavior without overexposing the window to solid white — the texture's own materials are mostly light/pastel, confirmed by rendering it in isolation).

**Two real bugs found and fixed while building this, both caught by rendering, not by reading the code:**
1. A `SubViewport` shares its parent's `World3D` by default unless `own_world_3d` is set — without it, the street scene's buildings/lamp posts/cars rendered directly into the real office (visible to the main camera, spawned inside the actual room), not just into the SubViewport's own texture. Fixed with `own_world_3d = true`, confirmed by re-rendering: the office room is clean again, and the SubViewport's own baked texture (checked directly, independent of the window material) shows the intended isolated street scene.
2. Applying the baked texture as window emission at the same multiplier the old flat "bfe3ff" color used overexposed the whole window to solid white — the backdrop's own materials are mostly light/pastel (white building facades, pale sidewalk), so full-strength emission of that texture blows out far brighter than a single flat color ever did. Fixed by scaling emission down to 12% while keeping albedo at full strength for lit detail.

Verified end to end through the real `Campaign` scene at two tiers (garage = a sparse single small building, premium_office = a denser skyline with a taller tower, more street furniture, cars) — the progression is visible through the glass, not just present in code. `tools/gpu_profile.gd` confirms the "low-cost" framing held in practice, not just intent: no measurable FPS/draw-call change across all three profiling scenarios (see `docs/performance/REAL_GPU_PROFILE.md`'s "Before/after the city-backdrop window pass").
