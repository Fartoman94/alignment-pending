# Known issues (release-candidate quality gate, P47)

Compiled from the whole P00-P47 implementation pass. None of these are open P0/P1 defects (things that crash, corrupt saves, or block the core loop) — `tools/bootstrap.sh` runs the full automated suite (hundreds of assertions, one block per prompt) clean with zero failures as of this writing. These are scope boundaries and environment limitations, each already called out honestly in `docs/production/IMPLEMENTATION_STATUS.md`'s per-prompt row when it was first hit.

## Scope boundaries (by design, not bugs)
- **No indoor/outdoor ambience crossfade** (`SERIOUS_REWORK_MASTER` pass) — the bundle's own `AudioDirector` template does this; the existing always-on adaptive-music bed already covers the "room tone" role, and the pass's time budget went to action-tied SFX (footstep/typing/chair/coffee, all synthesized) instead. See `docs/design/SERIOUS_REWORK_MASTER_REPORT.md`.
- **No dedicated "drink" animation** — the coffee-machine ambient visit still reuses the "talk" clip (no baked "drink" pose exists in the generated-humanoid rig, same gap `REAL_GAME_VISUAL_OVERHAUL_REPORT.md` already documented).
- **No per-role task-type visual distinction at the desk** — an engineer "debugging" vs. a researcher "training" would need `TaskManager` to track per-role task flavor at the desk level, which it doesn't; every desk-working agent still plays the same generic typing pose regardless of role.
- **No click-to-select system exists in the 3D world** (`CLAUDE_VISUAL_EXECUTION_MASTERPACK` Phase 7 audit) — `EventBus.selection_changed(kind, entity_id)` and `Hud._on_selection_changed()` are fully wired on the receiving end, but nothing anywhere emits that signal: no raycast-from-mouse, no building/staff picking, no selection highlight. Found while auditing Phase 7's "feedback selección" checklist item — this is dead plumbing, not a missing coat of polish, and building a real 3D picking + highlight system for the first time in a polish pass risked shipping something under-tested. See `docs/visual-progress/phase-07-report.md`.
- **`CityBackdrop`'s skyline stays a static, always-daytime bake even though the office's own day-night cycle now exists** (`REAL_GAME_VISUAL_OVERHAUL` pass) — it's a `SubViewport` rendered once with `UPDATE_ONCE` specifically for performance; re-baking it every frame to track time-of-day would defeat that. The two window panels it's viewed through do dim/brighten with the sun (their own material, decoupled from the backdrop texture itself).
- **Real alpha-blended reflective glass windows, a foliage-wind shader, and a spring-damper camera** (`REAL_GAME_VISUAL_OVERHAUL` pass's own `04_SHADERS`/`SPRING_CAMERA_RIG.gd` templates) were each evaluated and deliberately not adopted — see `docs/art/REAL_GAME_VISUAL_OVERHAUL_REPORT.md`'s priorities 6/7 for the reasoning (translucent windows risk a worse look with no exterior geometry behind them; the existing camera's exponential smoothing is the correct feel for a precise build-placement camera, not a bouncy follow-cam).
- `docs/design/ACHIEVEMENTS_AND_META.md` itself notes the achievement list is draft pending playtesting — content/thresholds may still change, though all 10 are now implemented (see "Resolved" below).
- **Steam integration is entirely local-mock** (P46): `PlatformService`/`PlatformBackend` is a real, working adapter architecture, but the only backend shipped is `LocalMockPlatformBackend` (achievements/cloud saves as local files). No real Steamworks SDK is integrated — none is an approved third-party dependency for this project. A real backend implements the same interface later without touching any caller.
- **150-agent stress scene has 16x CPU headroom, but "500 props" is unverified** (P44): no decorative prop-instancing system has been built by any prompt yet, so that specific `PERFORMANCE_BUDGET.md` stress target has no content to profile against.
- **"Complete vertical slice without mouse" verified on representative flows, not exhaustively** (P43): camera control, build placement, and menu/HUD focus navigation are directly tested end-to-end. Every other panel (staff hire, research start, model deploy/evaluate, incident response, settings) is built from the same focus-navigable Button/Slider primitives Godot drives via `ui_accept`/`ui_up`/`ui_down`/etc., which should generalize, but each one was not individually walked end-to-end without a mouse.

## Environment limitations hit during this pass
- **A custom Godot `Translation` resource crashes this project's Godot 4.7.2 headless build at shutdown** (P47/45): reproduced down to a *plain*, un-subclassed `Translation.new()` alone, no project code involved. Localization was built without `TranslationServer` as a result (see `LocalizationManager`). Worth re-testing against a future Godot patch release.
- **Only Linux (headless) has been tested at the engine/logic level; Windows runtime has never been exercised** — "Crash-on-boot tested on clean Windows/Linux environments" in `docs/production/RELEASE_CHECKLIST.md` is only half-verified. A Windows `.exe` is now built, packaged, and checksummed by `tools/export_release.sh` (cross-exported from Linux using the official Windows export templates, same source/logic already verified via `tools/bootstrap.sh`'s 199 assertions and the Linux binary's own `--qa-exported-smoke` pass), but it needs a real Windows machine to actually run and confirm — that hasn't happened.
- **Real *player-representative* hardware performance was never measured**: this development container happens to have a real X server and an AMD integrated GPU, so `tools/gpu_profile.gd` (finalization pass) now produces genuine GPU-rendered numbers — see `docs/performance/REAL_GPU_PROFILE.md` — averaging 55-60 FPS through an empty office, 20 staff, and the 150-staff stress scenario alike, with draw calls and primitive counts recorded. That's real evidence the render path itself isn't obviously broken, but it's still one specific integrated GPU in one specific dev container, not a player's discrete GPU or a defined minimum-spec machine, and it doesn't cover camera movement/build-mode/UI-churn costs. "60 FPS at 1080p on recommended hardware" from `PERFORMANCE_BUDGET.md` still needs a real run on an actual target machine before shipping.

## Resolved since P47 (finalization pass)
- ~~All characters (torso/arms/legs) read as sharp-edged boxes — Blender wasn't installed, so `ceo`/`cfo` also still had zero face geometry, procedurally patched as a stopgap~~ — resolved. Direct user feedback on a real screenshot of the actual running build ("los gráficos siguen siendo cuadrados y obsoletos"). The user installed Blender + the `python3-numpy` dependency its glTF exporter needs (both via their own `sudo`, never entered here); `tools/blender_generators/generate_humanoids.py` was reworked and all 30 character files (10 roles × 3 variants, including new `ceo`/`cfo` — no longer on the old flat-mesh pack) regenerated through it. Two real, non-obvious fixes found by rendering the result in Godot, not assumed from Blender's viewport: (1) raising bevel width/segments alone wasn't enough — the Bevel *modifier*'s generated geometry doesn't inherit smooth shading from the base mesh, so even a heavily-rounded shape still exported faceted; fixed by applying (baking) the modifier before calling `shade_smooth()` + angle-based auto-smooth. (2) Arms/legs deliberately push bevel width past half their own smallest dimension, which Blender's `clamp_overlap` rounds into a capsule shape instead of self-intersecting. Verified with real renders at three stages (isolated model, in-scene wide shot, in-scene close-up) — visibly smooth/rounded, not the old sharp-boxed look. `data/staff_roles.json` repointed for all 10 roles; `StaffAgent._add_face_details()`'s procedural-primitive fallback is now unreachable from any real role (kept only for the still-real mega-pack dev/showcase/smoke-test path — see its own doc comment).
- ~~4 of 10 draft achievements deferred (P46): "Known Unknowns", "Read the Memo", "Five Nines-ish", "Capacity Planning" each needed a tracking system this project didn't have yet~~ — resolved. Added real GameState tracking (`pending_safety_warnings`, `eval_warning_release_count`, `reliability_streak_days`, `capacity_clean_this_act`, all additive/no save migration needed) and wired all four in `AchievementManager`, none simplified/faked: "Known Unknowns" counts real Public releases with an incomplete evaluation; "Read the Memo" causally links a high-risk evaluation to a later (not same-day) deploy decision for that exact model; "Five Nines-ish" and "Capacity Planning" track sustained state (a 30-day reliability streak and a saturation-free campaign act) over real time. Verified via `tools/bootstrap.sh`. Caught and fixed a real GDScript engine quirk along the way: referencing another autoload's `const` by its global singleton name (e.g. `AchievementManager.SOME_CONST`) directly from `tests/smoke_test.gd` — the `--script`-loaded entrypoint, not an autoload itself — forces Godot to compile that autoload as a "depended script" before the autoload bootstrap sequence has registered `EventBus`, so a completely unrelated, unmodified autoload (`EvaluationManager`) failed to compile too. Confirmed by bisection (reverted each changed file one at a time until the failure isolated to this exact pattern). Fixed by using literal values with a comment instead, matching this file's own established convention of never doing this kind of static cross-autoload reference — every other autoload interaction here already goes through `get_root().get_node("XManager")`.
- ~~Content localization (P45): only code-authored UI strings routed through the pseudo-locale, hundreds of JSON-authored content strings were not wired~~ — resolved. `"es"` is now a real, complete, authored Spanish translation (703 strings: all 27 `data/*.json` catalogs, every static scene label, every dynamic UI template) wired end-to-end through the existing `LocalizationManager.tr_text()`/`localize_control_tree()` architecture, selectable from the Settings language dropdown, verified via `tools/bootstrap.sh`. The P45 pseudo-locale QA mechanism still exists unchanged, moved off `"es"` onto a non-player-facing `qa-pseudo` code. See `docs/design/LOCALIZATION_CONTENT.md`. Not yet reviewed by a native-speaker localization professional — see that doc's "Known limitation."
- ~~Binary export was never produced or tested~~ — resolved. Export templates for 4.7.2 stable are installed (downloaded from the official `godotengine/godot` GitHub release, SHA512-verified against its published `SHA512-SUMS.txt` before use — same verification already applied to the engine binary itself). `game/export_presets.cfg` is committed with `Linux` and `Windows Desktop` release presets. `tools/export_release.sh` reproducibly exports both, packages them, and smoke-tests the Linux binary standalone outside the editor via `--qa-exported-smoke` (see `docs/qa/EXPORTED_BUILD_SMOKE.md` for why that flag exists — Godot's `--script` CLI flag does not work against a packaged export, only an editable project, which is itself a real engine constraint worth knowing about). Windows *runtime* validation is still open, tracked above.
- ~~`ObjectDB`/`Resource` leak warnings at shutdown, unexplained~~ — investigated and documented in `docs/production/LEAK_INVESTIGATION.md`. Reproduced identically on a script with zero project code involved (2 `ObjectDB` instances leaked just from loading an SVG and saving PNGs); confirmed proportional to `ResourceLoader` cache activity, not to gameplay duration (the 150-agent/900-frame stress block inside the same process doesn't move the count). Runner/engine shutdown-ordering noise, not a project leak.
- ~~Staff are rendered as procedural capsule placeholders, no real character art~~ — mostly resolved. The project owner provided a real, finished 3D asset pack (`ALIGNMENT_PENDING_3D_ASSET_PACK`, 38 models) — `StaffAgent` now loads a real, authored low-poly character model per role (`game/assets/models/characters/*.glb`, wired via `StaffRoleCatalog`'s new `character_model` field) instead of building a capsule body from `ProceduralMeshFactory`, and 2 of the 3 buildables (`desk`, `server_rack`) now render their real matching models too (`BuildableCatalog`'s new `model` field → `BuildController._make_real_mesh()`; `safety_lab` has no matching asset in the pack and correctly falls back to its original procedural box). Verified in the actual running campaign scene each time — real screenshots of real staff and real furniture together, not just an isolated test scene. Found and fixed three real integration bugs this way, none of which the headless test suite alone would have caught: the pack's meshes are authored Z-up in local space (need a `-90°` X correction, same fix reused for buildables); on the first character attempt, that correction was applied to the wrong node so reparented limb/accessory meshes silently ended up outside it (whole character rendered sideways); and the ghost-preview vs. real-placement mesh paths had to be kept deliberately separate (translucent procedural box for the ghost stays clearer placement feedback than a detailed model silhouette would be). 30 of the 38 pack assets (the other 4 characters — ceo/cfo/hr/legal — plus all furniture variants beyond desk, all computer/equipment models, all datacenter-support models beyond server_rack, and all decorative props) are imported, validated, and viewable in `scenes/dev/asset_gallery.tscn`, but have no game system to wire into yet (no board/legal/HR visual context, no desk-decoration system, no prop-placement system) — see `docs/legal/ASSET_PROVENANCE.md`'s "3D asset pack integration" section for the full breakdown.

## Performance cost accepted, revisit if headcount scope grows
- **The 150-staff stress scenario drops from ~59 FPS avg to ~49 FPS avg (min 46) after wiring the real rigged/animated/faced `generated_humanoids` characters into `StaffAgent`'s `character_model_pool`** ([P-REWORK-02] integration pass) — see `docs/performance/REAL_GPU_PROFILE.md`'s before/after table. Real, expected cost: these are actual skinned meshes with a live `AnimationPlayer`, not the old flat billboard-style limb-pivot pack, so each one costs meaningfully more primitives/draw calls. Still comfortably 60 FPS at the realistic 20-staff mid-game scenario; 150 staff has no realistic in-game headcount analog this early. Per this project's own "profile, don't guess" policy, not treated as something needing LOD/pooling yet — revisit only if a future pass pushes realistic headcount scope past ~50-80 staff.
- **The renderer switch (`gl_compatibility` → `forward_plus`) plus SSAO/SSIL (`REAL_GAME_VISUAL_OVERHAUL` pass, `docs/art/REAL_GAME_VISUAL_OVERHAUL_REPORT.md`) drops the 150-staff stress scenario further, ~37.5 → ~34.9 FPS avg** — same "unrealistic scenario, don't chase it" call as above. The realistic 20-staff mid-game scenario is unaffected (59.6 vs 59.7 avg). The empty-office scenario showed a one-time min=1.0 FPS sample, almost certainly SSAO/SSIL's compute pipeline compiling on first use (a real but one-time cost, not sustained — avg only fell ~4 FPS) — not re-measured in isolation with a warm-up harness, flagged honestly rather than asserted as understood.

## UI bugs found, not yet fixed
- **`CityBackdrop`'s "dense" richness tier (premium_office/hq_building office windows) doesn't render a legible skyline** — visual audit pass. Found and fixed the dramatic instance of this (`tower.glb` at native scale dominating the whole 512×256 baked frame — see `docs/art/VISUAL_AUDIT_REPORT.md`), but even after removing it, the remaining `hq_building_exterior`/`mid_building_exterior` placements still read as one large, mostly-featureless flat panel rather than a recognizable skyline, confirmed by rendering the baked texture directly (`SubViewport.get_texture().get_image()`). Needs either a smaller scale, a farther Z position for those two buildings, or pulling the backdrop's own fixed camera (`Vector3(0, 1.7, 6.0)`, fov 55) back — any of which is a real, render-verifiable fix, just not one this pass had time to iterate on safely. Cosmetic only (a small decorative texture glimpsed through office windows, not something a player looks at directly) — not a crash or data-loss bug.

## UI bugs found and fixed
- ~~`Hud._show_world_panel()`'s rival/office-upgrade rows overflow the right panel's right edge instead of wrapping~~ — resolved, visual audit pass. Root cause found this time by printing real `Control.get_minimum_size()` down the whole `RightPanel/Margin/VBox/Scroll/DynamicContent` chain (not visible from reading the `.tscn`/`.gd` side by side, which is why the earlier pass that logged this couldn't find it): two `Label`s in `hud.gd` (`_show_world_panel()`'s "World state — ..." header, and `_build_real_estate_section()`'s building-listing description) were missing `size_flags_horizontal = SIZE_EXPAND_FILL`, so Godot's `Label.get_minimum_size()` reported their full un-wrapped single-line width (~600px) as a hard minimum, which a `VBoxContainer`/`MarginContainer` chain propagates upward as `max(anchor-rect, computed minimum)` — `Margin` was rendering 646px wide inside a 400px `RightPanel`. Fixed by adding the missing size flag (plus `autowrap_mode` on the one label that was missing that too); re-verified by printing the same rects post-fix (`Margin` now reports exactly 400×560, matching `RightPanel`) and by a real screenshot. See `docs/art/VISUAL_AUDIT_REPORT.md` for the full writeup.
