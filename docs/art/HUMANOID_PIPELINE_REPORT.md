# Humanoid pipeline report

Response to `ALIGNMENT_PENDING_TOTAL_VISUAL_AND_SYSTEM_REWORK`'s prompt 02 (`02_HUMANOID_PIPELINE.md`), which asked for real, rigged, faced, role-clothed humanoid characters generated via `03_BLENDER_GENERATORS/generate_humanoids.py`.

## Environment: Blender was not installed, installed it for real

This environment had no Blender. Installed Blender 5.0.1 from the official `blender.org` release tarball (Linux x64), checksum-verified against the published `SHA256` before extracting — same verification discipline this project already applies to the Godot engine binary and export templates. A local dev tool, not a shipped game asset/dependency — doesn't need the same approval gate `CLAUDE.md` requires for third-party assets bundled into the game itself.

## A real bug found and fixed, not assumed correct

The supplied `generate_humanoids.py` builds a real `Armature` (root/hips/spine/chest/neck/head, upper/lower arms+hands, upper/lower legs+feet) and separate primitive-mesh body parts, then bakes 5 real animations (idle/walk/typing/talk/sit) as pose-bone keyframes. But it only ever does `mesh.parent = armature_object` before export — a plain hierarchical parent, not a skin binding. No mesh vertex was ever assigned a bone weight, so the pose bones move but nothing visible follows them.

**Confirmed, not guessed**: ran the original script unmodified, loaded its export in Godot, screenshotted the idle pose, played the "walk" animation for 10 frames, screenshotted again — pixel-identical. The character would ship completely static regardless of which animation state code plays.

**Fixed** (`game/tools/blender_generators/generate_humanoids.py`, a corrected copy of the supplied script): a `bind()` helper adds a full-weight vertex group + a real `Armature` modifier to every body-part mesh, one bone each (the standard rigid-bind pattern for a blocky low-poly character where each part moves as one rigid unit — matching, not exceeding, the fidelity this project's existing procedural animation already has). Re-verified the same way: idle vs. walk frames now show a visibly different leg pose — `docs/art/screenshots/generated_humanoid_idle.png` vs. `generated_humanoid_walk.png`.

## What got generated

Full run, all 8 roles × 3 variants = 24 real character files in `game/assets/models/generated_humanoids/`. Spot-verified 3 roles side by side (`docs/art/screenshots/generated_humanoids_roles.png`) — researcher (labcoat + glasses), safety (vest + hard hat), team_leader (shirt + tie) — confirming role-specific accessories (glasses, helmet, tie) all still attach and export correctly after the fix, not just the base body. Every file has a real face (eyes, iris, pupils, brows, nose, mouth, ears) and real hair — none of this project's existing character models (from either supplied asset pack) have a face at all.

## Re-generated with softened facial features (direct response to "se ve demasiado mal" — [P-GIGA-03])

The 24 files above were wired into `StaffAgent` but still read as crude up close, confirmed by an actual close-zoom render, not assumed: the "glasses" were two near-black opaque cubes with almost no gap between them, reading as a solid mask across the eyes rather than lenses; the mouth was a wide, saturated near-red bar that read as garish rather than a closed mouth. Both are primitive-shape limitations of the generator's own approach (no textures, no lens transparency, no custom mouth curve), not a rendering bug.

Fixed by tuning `generate_humanoids.py`'s own values, not by adding new geometry: the glasses material lightened to a translucent-looking muted steel-blue (`(.32,.36,.42,1)`, roughness `.2` for a slight glass-like sheen) and shrunk (`.065→.055` width, `.045→.032` height); the mouth material changed from near-red `(.35,.05,.06,1)` to a muted rose `(.55,.33,.31,1)` and narrowed (`.07→.045` width). Re-ran the full generator (all 24 files regenerated, same Blender 5.0.1 install) and re-verified the exact same way as the original bug fix — rendered a close-up before/after, confirmed the skin-binding/animation still works post-regeneration (not assumed carried over: re-ran the 24-file individual routing check, zero failures), and ran `tools/bootstrap.sh` clean (214/214, after updating one more pre-existing test — see below).

**Also, per the same "no veo nada nuevo" pattern this session already hit once**: generating better characters isn't enough if the game still statistically prefers the old ones. `character_model_pool` for the 8 mapped roles previously mixed 6 old flat-mesh mega-pack entries (faceless capsule-style characters, confirmed by close-up render to be the actual thing the user was reacting to) with only 3 generated entries — a ~67% chance of the worse model on every hire. `data/staff_roles.json` now points `character_model` and `character_model_pool` at *only* the 3 generated variants for those 8 roles, so every hire in a mapped role gets a real face, every time. `ceo`/`cfo` (2 roles, no generated variants exist) are unchanged, still mega-pack only — a known, real gap, not silently dropped.

`tests/smoke_test.gd`'s general 50-agent character-build test (distinct from the mega-pool-specific one already updated earlier this session) assumed every role's default `character_model` builds flat-mesh limb pivots — no longer true for 8 of 10 roles now that they default straight to a skeletal model. Updated with the same `_is_skeletal` branch as the other test, not weakened.

## Wired into `StaffAgent` — done, verified, live in-game

`StaffAgent._build_visual()` now auto-detects, per model, whether it has a `Skeleton3D` + `AnimationPlayer` and branches to a real parallel skeletal-animation path (`_build_visual_skeletal()`) instead of the flat-mesh pack's pivot construction — no reparenting, the skeleton handles posing directly. The two paths coexist; nothing about the existing flat-mesh characters changed.

1. **Detection & build** — `_find_animation_player()`/`_find_skeleton()` walk the instantiated model; if an `AnimationPlayer` is found, `_build_visual_skeletal()` takes over. Every baked clip (idle/walk/typing/talk/sit) had its `loop_mode` forced to `Animation.LOOP_LINEAR` — the generator bakes clips with no explicit loop mode, which defaults to play-once-and-freeze; confirmed by rendering "walk" and watching it freeze mid-stride before the fix.
2. **State → animation** — `_animate_visual_skeletal()` maps `StaffAgent.State` to a clip name (`IDLE`→`idle`, `MOVING`→`walk`, `WORKING`→`typing`) and calls `AnimationPlayer.play()` only when the target clip actually changes (confirmed by rendering: calling `.play()` every physics frame visibly froze the character instead of animating it).
3. **Per-instance variation** — `_apply_variation_skeletal()` finds `Head`/`Hair` children directly under the `Skeleton3D` (capitalized, the generator's own convention; never reparented, since a skinned mesh's skeleton reference is a `NodePath` that would break if moved) and applies the same per-instance skin-tone/hair-tint variation the flat-mesh path already does.
4. **Orientation** — confirmed by rendering 4 cardinal angles: these models' front already faces local +Z at `rotation.y == 0`, the same convention every other character pack in this project uses. No corrective rotation needed, unlike the flat-mesh path's -90° X fix for the mega-pack.

**Verified through the real game code path, not a synthetic shortcut**: built a probe that calls the actual `assign_work()` entry point (same one `Campaign` uses) against a synthetic `NavigationRegion3D`, then rendered and inspected `current_animation` at each stage — idle → walk (while pathing to the target) → typing (on arrival/WORKING) all played the correct, visually distinct clip. Also force-built one `StaffAgent` per each of the 24 generated files individually: all 24 correctly set `_is_skeletal = true` and get a real `AnimationPlayer`, zero failures.

**Wired into the actual role pool**, not just possible to use: `data/staff_roles.json`'s `character_model_pool` now includes all 3 generated variants for the 8 roles the generator covers (`researcher`, `engineer`, `data_ops`, `safety_analyst`→`safety`, `product_manager`→`team_leader`, `support_specialist`→`support`, `legal_specialist`→`legal`, `hr_partner`→`hr`), alongside the pre-existing mega-pack entries — every new hire in those roles has a real chance of spawning a fully rigged, faced, animated character, mixed in with the older flat-mesh ones. `ceo`/`cfo` keep their existing mega-pack models; the generator's `ROLES` list doesn't cover them.

**Smoke suite updated to match, not skipped**: `tests/smoke_test.gd`'s mega-pack pool-pick regression test iterated `researcher`'s full `character_model_pool` (now a mix of flat-mesh and skeletal entries) at 12 fixed seeds and asserted every pick builds the flat-mesh pack's 4 limb pivots — a real, deterministic seed rolled a skeletal entry and correctly failed that assertion (it has no limb pivots by design). Fixed by branching the assertion on `_is_skeletal`: skeletal picks are checked for a real `AnimationPlayer` instead. All 214 smoke assertions pass clean after the fix.

**Performance cost is real, measured, and accepted** — see `docs/performance/REAL_GPU_PROFILE.md`'s before/after table for this pass. The 150-staff stress scenario drops from ~59 to ~49 FPS avg (skinned meshes with a live `AnimationPlayer` cost more than the old flat billboard-style pack); the realistic 20-staff mid-game scenario stays comfortably at 60 FPS. Documented in `docs/production/KNOWN_ISSUES.md` as an accepted cost to revisit only if realistic headcount scope grows well past 150.

## Known, deliberately deferred gap: scale mismatch

Rendered a generated character next to an existing `desk_single.glb` and an existing StaffAgent character, same camera, same depth (`docs/art/screenshots/generated_humanoid_scale_check.png`): height matches closely (~3.5% difference, not visually distracting), but the new characters read as noticeably wider/bulkier than the flat-mesh pack's characters up close. No `model_scale` correction has been applied — deferred because it's cosmetic (not a functional bug, no clipping/collision issue observed) and a width-only correction risked distorting the generator's own proportions rather than fixing a true uniform scale-authoring mismatch. Tracked, not silently dropped.
